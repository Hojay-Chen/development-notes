# 一、Kafka 消息队列篇

## 1. 为什么需要消息队列？

在分布式系统里，最直观的通信方式就是**服务之间直接调用**：订单服务下单成功后，直接调用支付服务、库存服务、通知服务……每个调用都是同步的 HTTP 请求。

这种"直连"在服务少、流量小时没有太大问题，但规模一大，三个毛病立刻显现：

1. **强耦合**：调用方必须知道被调方的一切（地址、协议、出参入参）。想加一个下游（比如"下单后发短信"），就得改上游代码重新发版；任何一方挂了，整个调用链跟着失败。
2. **无缓冲**：下游的处理能力是有限的。秒杀瞬间涌来 10 万下单请求，下游数据库直接被打穿——直连模式下没有地方"挡"一下。
3. **同步阻塞**：调用方要干等所有下游返回。下单耗时 = 支付耗时 + 库存耗时 + 通知耗时 + ……链路越长，延迟越大，而大部分时间只是在**干等**。

![直连调用与消息队列对比](https://raw.githubusercontent.com/Hojay-Chen/development-note-resource/main/images/kafka_mq_why.png)

**消息队列做了什么**：**消息队列（Message Queue，MQ）** 就是在生产方和消费方中间加一层"中转站"。可以把它类比成**邮局**：寄信人（生产者）把信投进邮筒（MQ），收信人（消费者）什么时候有空什么时候来取，双方互不感知对方的存在。

> **核心思想**：直连调用把生产方与消费方**强绑定**；MQ 在中间插一层缓冲，把"同步强耦合"变成"异步解耦"。

由此换来三大好处：

| 好处 | 直连时的场景 | 引入 MQ 之后 |
| :--- | :--- | :--- |
| **解耦** | 加一个下游就要改上游代码 | 上游只往 MQ 发消息，下游谁订阅谁接 |
| **削峰填谷** | 高峰请求直接压垮下游 | 高峰先灌进 MQ，下游按自身能力慢慢消费 |
| **异步** | 下单要同步等所有下游 | 发完消息立刻返回，下游异步处理 |

## 2. Kafka 核心架构与基本概念

**Kafka** 是一个**分布式发布-订阅消息系统**，由 LinkedIn 开源、Apache 顶级项目。它最出名的是**高吞吐**：单集群可以支撑每秒百万级消息，同时消息可以**持久化**在磁盘上、支持多副本、可水平扩展。

先看整体架构：

![Kafka 整体架构](https://raw.githubusercontent.com/Hojay-Chen/development-note-resource/main/images/kafka_architecture.png)

围绕上图，记住几个核心概念：

| 概念 | 一句话解释 | 类比 |
| :--- | :--- | :--- |
| **Producer（生产者）** | 产生并发送消息的一方 | 寄信人 |
| **Consumer（消费者）** | 拉取并处理消息的一方 | 收信人 |
| **Broker** | Kafka 集群中的一台服务器节点 | 一个邮局分局 |
| **Topic（主题）** | 消息的逻辑分类，比如"订单消息""日志消息" | 一个信件分类 |
| **Partition（分区）** | 一个 Topic 被拆成的物理分片 | 一排货架 |
| **Offset（偏移量）** | 分区内消息的递增编号，从 0 开始 | 货架上箱子的编号 |
| **Consumer Group（消费者组）** | 一组协同消费的消费者 | 一个收件团队 |

其中 **Topic 与 Partition** 的关系是整个 Kafka 最核心的抽象，值得单独展开：

![Topic 分区与有序性](https://raw.githubusercontent.com/Hojay-Chen/development-note-resource/main/images/kafka_topic_partition.png)

- **Topic 是逻辑概念，Partition 是物理概念**。一条 Topic 的消息会被拆到多个 Partition 里，每个 Partition 是一个**独立的日志文件**，分布在不同的 Broker 上。
- **分区内有序，分区间无序**：消息在分区内按 Offset `0→1→2→3` 严格递增（写在文件末尾），但不同分区之间**没有全局顺序**。想要"同一订单的消息严格有序"，就按 key 哈希路由到同一个分区。
- **分区 = 并发与扩展的基础**：分区越多，可以并行写入/消费的通道就越多。Kafka 的**并行度上限就是分区数**。

> **为什么必须分区？** 单台机器的磁盘容量和吞吐都有上限。把数据拆到多个分区分摊到多台 Broker 上，才能"分而治之"——这也是 Kafka 能水平扩展到海量数据的关键。

## 3. 高吞吐的秘密

Kafka 常被拿来和 RocketMQ、RabbitMQ 比，最突出的差异就是**吞吐量**。同样是消息队列，Kafka 凭什么能到百万级 TPS？主要靠下面四板斧。

### 3.1 顺序写磁盘：把"随机写"变成"追加写"

传统消息中间件把每条消息当独立数据随机落盘，磁盘要频繁**移动磁头寻道**，而寻道是机械盘最慢的操作（一次约 10ms）。Kafka 反其道而行：**消息按分区追加到日志文件末尾**，是纯粹的**顺序写**。

![随机写与顺序写对比](https://raw.githubusercontent.com/Hojay-Chen/development-note-resource/main/images/kafka_sequential_write.png)

> **顺序写的威力**：机械磁盘顺序写可以到 100~200MB/s，而随机写往往不到 1MB/s，差了两个数量级。这也是 Kafka"用磁盘却不慢"的底气——**它把磁盘当内存用**。

### 3.2 Page Cache：读写都先在内存里

Kafka 写入的消息先进入操作系统的**页缓存（Page Cache）**，由操作系统决定何时真正落盘；消费时也优先从页缓存读。因为生产端和消费端通常"一前一后"，消费者读的往往正是生产者刚写入、还在缓存里的数据，**命中率极高**，绝大多数情况下根本不用碰磁盘。

### 3.3 零拷贝：把数据直接送到网卡

消息要发给消费者时，传统做法要经历 4 次数据拷贝（磁盘→内核 buffer→用户 buffer→内核 socket buffer→网卡）和 4 次内核态/用户态切换。Kafka 用 Linux 的 **`sendfile` 零拷贝**，让数据从**磁盘直接到网卡**，绕过了用户态，拷贝次数从 4 次降到 2 次。数据量大时，省下的时间非常可观。

### 3.4 批量与压缩：一次网络请求传一大包

Kafka 不一条一条发消息，而是**攒批（batch）**发送：生产者把一批消息攒起来打包一次发送，消费者同样一批一批拉取。批内还能用 `lz4`/`zstd` 压缩。批量 + 压缩极大减少了网络往返和传输字节数。

> **一句话总结**：分区并行 × 顺序写 × 页缓存 × 零拷贝 × 批量压缩——这五项叠加，构成了 Kafka 百万级吞吐的基石。

## 4. 消费者组：点对点与发布订阅

Kafka 的消费模型围绕**消费者组（Consumer Group）**展开，它同时实现了消息队列的两种经典模式：

- **点对点（Queue）**：同一组内的消费者**共同分担**一个 Topic 的消息，一条消息只会被组内一个消费者处理。
- **发布订阅（Pub/Sub）**：不同消费者组之间**互不影响**，每个组都能消费到全部消息。

![消费者组的分区分配](https://raw.githubusercontent.com/Hojay-Chen/development-note-resource/main/images/kafka_consumer_group.png)

分区在组内怎么分配？规则只有一条：

> 在同一个消费者组内，**每个分区同时只分配给一个消费者**；但一个消费者可以持有多个分区。

所以：

- **组内**：`分区数 ≥ 消费者数` 时，一个消费者负责一个或多个分区；如果消费者比分区多，多出来的消费者**空闲**（拿不到分区）。因此**分区数决定了组内的最大并行度**。
- **组间**：Group A 和 Group B 都可以各自消费 Topic 的全部消息，互不干扰。

**Rebalance（再平衡）**：当消费者加入/退出、或分区数变化时，Kafka 协调者（Coordinator）会把分区在组内重新分配，这一过程叫 Rebalance。它保证了"组内不重不漏"，但也意味着短暂的不可用——所以**组内成员不宜频繁变动**。

### 4.1 Offset：消费到哪里了

消费者拉取消息后，需要把**消费进度**记下来，否则重启后不知道从哪接着读。这个进度就是 **Offset**：

![消费进度：已提交 offset 与当前读取位置](https://raw.githubusercontent.com/Hojay-Chen/development-note-resource/main/images/kafka_offset.png)

- 分区日志里的每条消息都有一个递增 Offset。
- 消费者每处理一批消息，就**提交（commit）**一个已提交 Offset；Kafka 把它记在内部主题 `__consumer_offsets` 里。
- 消费者崩溃重启后，从**已提交的 Offset** 继续读——注意，是"已提交"的位置，而不是"最后读到"的位置。

> **至少一次（At-Least-Once）**：默认情况下消费者"先处理业务、后提交 Offset"。如果处理完、还没提交就宕机，重启后会**重读刚才那批消息**，导致**重复消费**。这是 Kafka 默认的语义，业务方需要配合**幂等处理**来兜底。

## 5. 消息可靠性：不丢不重

保证消息不丢、不重，要在**三个端**分别做文章：生产端、存储端（Broker）、消费端。

### 5.1 生产端：acks 确认机制

生产者发消息后，要"等到什么程度"才算成功？Kafka 用 `acks` 参数控制：

![生产端 acks 确认机制](https://raw.githubusercontent.com/Hojay-Chen/development-note-resource/main/images/kafka_producer_acks.png)

| 配置 | 行为 | 可靠性 | 性能 |
| :--- | :--- | :--- | :--- |
| `acks=0` | 发出去就算成功，不等任何确认 | 可能丢消息 | 最快 |
| `acks=1` | Leader 写入本地日志即确认 | Leader 宕机可能丢 | 较快 |
| `acks=all` | 等**所有 ISR 副本**都确认才返回（Kafka 3.0+ **默认**） | 最安全 | 略慢 |

生产端还有个"防重"的配套：**幂等生产者**（`enable.idempotence=true`，0.11+ 引入，Kafka 3.0+ **默认开启**）。它给每条消息加序列号，Broker 端去重，即使网络重试也不会把同一条消息写两次。幂等生产者 + `acks=all`，再加上**事务（Transactional API）**，就能做到生产者端**精确一次（Exactly-Once）**。

### 5.2 存储端：副本与 ISR

光有生产者确认还不够——如果 Leader 把消息存进自己本地就返回成功，可它随后宕机了，这条消息照样丢。所以 Kafka 给每个分区保存**多个副本**：

![副本与 ISR 故障转移](https://raw.githubusercontent.com/Hojay-Chen/development-note-resource/main/images/kafka_replication.png)

- 每个分区有一个 **Leader** 和多个 **Follower**。**所有读写都走 Leader**，Follower 只负责从 Leader 拉取数据、保持同步。
- **ISR（In-Sync Replicas，同步副本集合）**：与 Leader 保持同步的副本组成的集合。`acks=all` 等的就是 ISR 全部确认。
- **Leader 宕机时**：从 ISR 中选举出一个新 Leader，其余 Follower 继续向它同步。**不在 ISR 里的副本没有当选资格**——因为它落后太多，选了它就可能丢数据。

> **可靠性的核心取舍**：副本数越多越安全，但写入要等更多副本确认，延迟越高。一般生产环境 `replication.factor=3`、`acks=all`，在安全与性能之间取平衡。

### 5.3 消费端：offset 提交时机决定语义

消费端的"不重"取决于**提交 Offset 的时机**，而"不丢"取决于**业务处理与提交的顺序**：

| 提交策略 | 顺序 | 语义 | 后果 |
| :--- | :--- | :--- | :--- |
| **自动提交**（默认 `enable.auto.commit=true`） | 每 5 秒定时提交 | 至少一次 | 宕机可能重复，也可能丢一小段（处理未跟上提交） |
| **先提交、再处理** | 提交 → 处理 | 最多一次 | 宕机可能丢消息，但绝不重复 |
| **先处理、再手动提交** | 处理 → 提交 | 至少一次 | 可能重复，但绝不丢 |
| **处理 + 幂等/事务** | 处理时去重 | 精确一次 | 不丢不重，最可靠 |

> **实践建议**：绝大多数业务选"**先处理业务逻辑，再手动提交 Offset**"，配合**业务侧幂等**（唯一键去重、状态机判断），以最小的代价获得"不丢不重"。

## 6. 总结与对比

### 6.1 Kafka vs RocketMQ vs RabbitMQ

| 对比项 | Kafka | RocketMQ | RabbitMQ |
| :--- | :--- | :--- | :--- |
| **定位** | 分布式流平台（日志/数据管道） | 分布式消息中间件（金融/电商） | 轻量 AMQP 消息队列 |
| **语言** | Scala / Java | Java | Erlang |
| **吞吐** | **百万级 TPS** | 十万级 TPS | 万级 TPS |
| **有序性** | 分区内有序 | 队列内有序 | 单队列有序 |
| **延迟** | 毫秒级（批量攒批略增延迟） | 毫秒级 | **微秒级** |
| **可靠性** | ISR 副本机制 | 主从同步 / DLedger | 镜像 / Quorum 队列 |
| **事务消息** | 支持（0.11+ 事务 API） | 支持（半消息机制，最成熟） | 不支持 |
| **延迟/定时消息** | 不支持 | 支持（最灵活） | 支持（TTL + 死信） |
| **消息轨迹** | 需自建 | 内置 | 插件支持 |
| **适用场景** | 日志采集、埋点、大数据流计算 | 交易、订单、削峰场景 | 中小规模业务解耦、RPC 异步 |

> **选型口诀**：要**吞吐和流处理**选 Kafka；要**金融级事务消息**选 RocketMQ；要**功能丰富、延迟极低的小规模解耦**选 RabbitMQ。

### 6.2 核心要点

1. **MQ 的价值**：解耦、削峰填谷、异步——本质是在生产方和消费方之间加一个缓冲层。
2. **分区是 Kafka 的基石**：有序性、并行度、负载均衡都以分区为单位；**分区内有序、分区间无序**。
3. **高吞吐的秘密**：分区并行 + 顺序写磁盘 + Page Cache + 零拷贝 + 批量压缩。
4. **消费者组**：组内分区独占（点对点），组间独立消费（发布订阅）；**并行度上限 = 分区数**。
5. **可靠性三端**：生产端 `acks`、存储端 ISR 副本、消费端 Offset 提交时机。
6. **默认至少一次**：先处理、后提交 → 可能重复；要做"精确一次"，必须配合幂等或事务，付出性能代价。

### 6.3 典型应用场景

- **日志与埋点采集**：Kafka 最经典的场景。前端/服务产生的海量日志、用户行为埋点，先写入 Kafka，再交给大数据平台消费分析。
- **异步解耦**：订单创建后发一条消息，积分、短信、搜索、推荐各自订阅处理，互不拖累。
- **削峰填谷**：秒杀、大促时把瞬间流量先灌进 Kafka，下游按处理能力慢慢消费，保护数据库。
- **实时数据管道**：作为 Flink/Spark Streaming 的上游数据源，支撑实时数仓、实时风控。
- **事件驱动架构**：微服务之间通过 Topic 发布领域事件，实现最终一致性与事件溯源。

> **一句话收尾**：Kafka 用"分区 + 顺序写 + 副本"三个设计，同时拿到了高吞吐、可扩展和可持久化；理解它，重点就落在 **Topic/Partition 的分片模型、消费者组的消费模型、以及三端可靠性机制**这三件事上。
