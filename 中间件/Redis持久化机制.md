# 一、Redis 持久化机制篇

## 1. 为什么需要持久化？

Redis 之所以这么快，一个关键原因就是**所有数据都存在内存（RAM）里**——读写都在内存中完成，单次操作通常只要微秒级。

但这就带来了一个致命问题：**内存是易失的**。一旦 Redis 进程退出、服务器宕机、或者断电，内存里的数据就会**瞬间全部丢失**。

![内存数据在宕机时全部丢失](https://raw.githubusercontent.com/Hojay-Chen/development-note-resource/main/images/redis_why_persist.png)

> **核心痛点**：Redis 是内存数据库，宕机或重启后内存数据会全部清空。如果这些数据只是"缓存"，丢了可以从数据库回源重建；但如果 Redis 里存的是**丢不起的业务数据**——比如登录会话、购物车、计数器、排行榜、限流统计——就必须想办法把数据**持久化到磁盘**，这样重启后才能恢复。

Redis 为此提供了两种持久化机制，它们是后续所有方案的基础：

- **RDB（Redis DataBase）快照**：周期性把内存中的**全量数据**拍一张"照片"存到磁盘。
- **AOF（Append Only File）日志**：把每一条**写命令**都追加记录到日志文件里。

这两种机制各有利弊，而且它们不是非此即彼的关系——Redis 4.0 之后还可以把两者**混合**使用。下面我们先把两种机制各自讲透，再讲它们怎么配合。

---

## 2. RDB 快照持久化

### 2.1 原理：给内存拍一张快照

RDB 的思路非常朴素：**每隔一段时间，把内存中的全量数据序列化后写入磁盘，生成一个二进制的快照文件 `dump.rdb`**。

可以把它类比成"**拍照/存档**"——照片拍下的那一刻，内存里有什么，快照里就有什么。之后你再怎么改数据，这张照片都不会变，直到下一次拍照。

![RDB 快照写入磁盘](https://raw.githubusercontent.com/Hojay-Chen/development-note-resource/main/images/redis_rdb_snapshot.png)

### 2.2 触发方式

RDB 快照不是随时都拍的，它有几种触发时机：

- **手动 `SAVE`**：主进程**同步**生成快照。生成期间主进程阻塞，无法处理任何读写命令——**生产环境基本不用**。
- **手动 `BGSAVE`**：`fork` 一个子进程，由**子进程**去生成快照，主进程不阻塞、继续服务。这是手动触发的推荐方式。
- **自动触发**：通过 `save` 配置项，满足条件自动执行 `BGSAVE`：

  ```
  save 900 1        # 900 秒内至少有 1 次写操作，就触发一次快照
  save 300 10       # 300 秒内至少有 10 次写操作，就触发一次快照
  save 60 10000     # 60 秒内至少有 10000 次写操作，就触发一次快照
  ```

  只要满足其中任意一条，Redis 就会自动执行一次快照。

### 2.3 BGSAVE 的秘密：fork + 写时复制

`BGSAVE` 之所以不阻塞主进程，靠的是操作系统提供的 `fork()` 机制和**写时复制（Copy-On-Write，COW）**，流程如下：

![BGSAVE fork 子进程 + 写时复制](https://raw.githubusercontent.com/Hojay-Chen/development-note-resource/main/images/redis_rdb_bgsave.png)

1. **fork 子进程**：主进程调用 `fork()` 创建子进程。子进程与父进程**共享同一份内存页表**，此时子进程看到的内存就是父进程 fork 那一刻的完整数据。
2. **子进程写快照**：子进程按照自己看到的内存，把全量数据序列化写入 `dump.rdb`，这个过程对主进程**零打扰**。
3. **主进程继续服务**：fork 之后主进程照常处理读写请求。如果主进程此时要**修改**某块内存，由于写时复制，这块内存页会先被**复制一份**，主进程改的是副本，子进程读的仍是 fork 那一刻的旧页。
4. **快照一致**：因为子进程始终读的是"fork 那一刻"的内存，所以生成的快照天然是**某一时间点的一致数据**，不会出现写到一半数据变来变去的脏快照。

> **写时复制的代价**：fork 瞬间主进程会**短暂阻塞**（要复制页表）；同时，快照生成期间如果有大量写入，主进程会因为复制内存页产生**额外的内存开销**。数据量越大，这两个成本越明显。

### 2.4 优点与缺点

**优点：**

- **文件紧凑**：RDB 是压缩过的二进制文件，体积小，非常适合**备份、灾备、跨机器迁移**（把 `dump.rdb` 拷走即可）。
- **恢复速度快**：恢复时直接**批量载入**数据，而不是像 AOF 那样一条条重放命令，大数据量下恢复明显更快。
- **对主进程影响小**：`BGSAVE` 由子进程完成，正常情况下主进程几乎无感知。

**缺点：**

- **丢数据窗口大**：快照是**周期性**的，两次快照之间的写入，一旦宕机就会**全部丢失**。比如配置了 `save 900 1`，极端情况下可能丢 15 分钟的数据。
- **全量快照成本高**：每次都是**全量**序列化，数据量大时 fork 阻塞、COW 内存翻倍、写磁盘耗时都很可观，所以快照频率没法提得太高——这又反过来放大了丢数据的窗口。

> **RDB 的核心矛盾**：快照频率太低会丢很多数据，频率太高又扛不住全量快照的开销。能不能换一种思路，把代价从"全量"摊到"每条命令"上？——这就是 **AOF** 要解决的问题。

## 3. AOF 日志持久化

### 3.1 原理：把每条写命令记下来

AOF 的思路和 RDB 完全相反：**不是存"数据"，而是存"命令"**。客户端每发来一条写命令（`SET`、`DEL`、`INCR`…），Redis 在执行的同时把这条命令**追加**到日志文件 `appendonly.aof` 末尾。

可以类比成"**记账本**"：每一笔交易都记一笔账，将来想恢复，就把账目从头到尾重放一遍，数据就回来了。

![AOF 写命令追加流程](https://raw.githubusercontent.com/Hojay-Chen/development-note-resource/main/images/redis_aof_append.png)

**为什么记录命令，而不是像 RDB 那样记录数据？** 原因有三：

1. **Redis 命令集足够简单**：Redis 的命令就是原子操作，没有 MySQL 那种复杂的多表关联、事务依赖，**重放命令就能精确还原数据**。
2. **追加是顺序写**：在末尾追加一条记录是磁盘**顺序写**，开销远比全量快照低，所以可以做到"每条命令都记录"，天然弥补了 RDB 丢数据窗口大的问题。
3. **可读可修**：AOF 文件是文本格式（RESP 协议），人可以直接打开看，甚至手动**删掉误操作的那条命令**再重启恢复。

### 3.2 写流程与三种 fsync 策略

AOF 的写入并非"每条命令立刻落盘"，中间还隔着一层缓冲，完整流程是：

1. 客户端发送写命令；
2. Redis **主进程执行命令**、修改内存（此时命令已经生效）；
3. 命令被**追加到 AOF 缓冲区**（内存）；
4. 按照配置的 `appendfsync` 策略，把缓冲区内容**写入并 fsync 到磁盘**的 `appendonly.aof` 文件。

其中第 4 步的"什么时候真正落盘"，直接决定了**数据安全**与**性能**的取舍。`appendfsync` 有三种策略：

| 策略 | 行为 | 丢数据风险 | 性能 |
| :--- | :--- | :--- | :--- |
| `always` | 每条写命令都 fsync 到磁盘 | **几乎不丢**（最多丢正在写的那一条） | 最慢 |
| `everysec` | 每秒 fsync 一次（**默认**） | **最多丢 1 秒**的数据 | 较快 |
| `no` | 不主动 fsync，交给操作系统决定落盘时机 | 可能丢较多数据 | 最快 |

> **为什么默认是 `everysec`？** 因为 Redis 本身是单线程处理命令，如果每条命令都 `fsync`，磁盘的写入速度会成为整个 Redis 的瓶颈；而 `no` 又太不安全。`everysec` 把 fsync 交给后台线程每秒做一次，既能保证**最多只丢 1 秒数据**，又不拖慢主线程——这是数据安全与性能的折中。

### 3.3 AOF 重写：解决文件膨胀

AOF 有个与生俱来的毛病：**文件会无限膨胀**。假设业务对同一个 key 执行了 1000 次 `INCR`，AOF 文件里就会躺着 1000 条 `INCR` 命令；文件越大，重启恢复时重放就越慢，还白占磁盘空间。

![AOF 重写前后对比](https://raw.githubusercontent.com/Hojay-Chen/development-note-resource/main/images/redis_aof_rewrite.png)

解决手段是 **AOF 重写（rewrite）**。注意，重写**不是**把旧文件改小，而是：

> **AOF 重写的本质**：根据内存中**每个 key 的当前最新值**，生成一组能表达最终状态的最少命令，写入一个**全新的 AOF 文件**，然后切换使用。上面那 1000 条 `INCR`，重写后就变成一条 `SET key 1000`。

重写由 `BGREWRITEAOF` 触发，过程和 `BGSAVE` 类似：也是 `fork` 一个子进程，基于子进程看到的内存快照生成新文件；期间主进程照常服务，同时把新产生的写命令记入一个**重写缓冲区**，待子进程写完新文件后**合并**进去，保证新文件不丢重写期间的数据。

重写还可以**自动触发**：当 AOF 文件大小超过上次重写后大小的 `auto-aof-rewrite-percentage`（默认 100%，即翻倍）且大于 `auto-aof-rewrite-min-size`（默认 64MB）时自动执行。

### 3.4 优点与缺点

**优点：**

- **丢数据少**：`everysec` 策略下最多丢 1 秒数据，`always` 几乎不丢——这是相比 RDB 最大的优势。
- **可读可修**：文本格式，可以人工检查，甚至能**手动删除误操作命令**后恢复（这在 RDB 里做不到）。

**缺点：**

- **文件体积大**：记录的是命令，同样数据量下 AOF 文件通常比 RDB 大得多。
- **恢复速度慢**：重启时要**逐条重放**命令，数据量大时明显慢于 RDB 的批量载入。
- **极端情况下也有阻塞**：虽然 `everysec` 交给后台线程，但高负载时 AOF 写盘、重写仍可能带来延迟波动。

> **RDB 与 AOF 恰好互补**：RDB 体积小、恢复快，但丢数据多；AOF 丢数据少，但体积大、恢复慢。**能不能把两者优点合在一起？**——这就是混合持久化。

## 4. 混合持久化与加载优先级

### 4.1 Redis 4.0 混合持久化

Redis 4.0 引入了**混合持久化**，配置项为 `aof-use-rdb-preamble yes`。它的核心思想是**让 AOF 文件"先 RDB 后 AOF"**：

> **混合持久化原理**：重写 AOF 时，不再把最终状态写成纯命令，而是**先用 RDB 格式写入一个全量快照**（作为 AOF 文件的头），**再在后面追加**重写之后产生的增量命令。这样一份 AOF 文件 = **RDB 全量快照（前缀） + AOF 增量命令（后缀）**。

重启恢复时，Redis 先**快速加载 RDB 部分**拿到全量数据，再**重放少量的 AOF 增量命令**补上快照之后的新数据。于是：

- **恢复速度**：接近 RDB（跳过了一大段命令重放）；
- **数据安全**：接近 AOF（增量部分还能继续记录到秒级）。

### 4.2 重启加载优先级

如果两种持久化都开启了，Redis 重启时会加载哪个文件？答案是**优先 AOF**：

![Redis 重启加载流程](https://raw.githubusercontent.com/Hojay-Chen/development-note-resource/main/images/redis_load_priority.png)

1. Redis 启动，先检查 **AOF 是否开启且文件存在**；
2. 若 AOF 可用，**直接加载 AOF** 恢复数据；
3. 否则，退而加载 **RDB** 文件；
4. 两者都没有，则从空数据启动。

**为什么 AOF 优先？** 因为 AOF 记录的写命令**比 RDB 快照更新**、丢失的数据更少，恢复出来的数据更接近宕机前的状态。这是"用更安全的数据源恢复"的朴素原则。

## 5. 总结与工程实践

### 5.1 RDB vs AOF 对比

| 对比项 | RDB 快照 | AOF 日志 |
| :--- | :--- | :--- |
| **记录内容** | 内存数据的全量二进制快照 | 每一条写命令 |
| **文件格式** | 压缩二进制 | 文本（RESP 协议） |
| **文件大小** | 小 | 大（命令冗余） |
| **丢数据风险** | 大（两次快照之间全丢） | 小（`everysec` 最多丢 1s） |
| **恢复速度** | 快（批量载入） | 慢（逐条重放） |
| **对主进程影响** | fork 阻塞 + COW 内存开销 | 写盘/重写带来延迟波动 |
| **适用场景** | 备份、灾备、主从全量同步 | 数据安全要求高的主存储 |

### 5.2 核心要点

1. **持久化的动机**：Redis 是内存数据库，宕机/重启数据会全丢，存了丢不起的业务数据就必须持久化。
2. **RDB = 全量快照**：周期性把内存数据拍成照片，靠 `fork` + 写时复制不阻塞主进程；体积小、恢复快，但丢数据窗口大。
3. **AOF = 写命令日志**：把每条写命令追加到文件，`everysec` 策略下最多丢 1 秒数据；文件膨胀用**重写**解决。
4. **混合持久化（4.0+）**：AOF 文件 = RDB 全量前缀 + AOF 增量后缀，兼顾恢复速度与数据安全；重启**优先加载 AOF**。

### 5.3 生产建议

- **纯缓存场景**（数据可重建）：可直接**关闭持久化**（`save ""` 且 `appendonly no`），把磁盘和 fork 开销省下来。
- **数据丢不起的场景**：开启混合持久化（`aof-use-rdb-preamble yes`）+ `appendfsync everysec`，兼顾安全与性能；要求极高的业务可上 `always`。
- **定时备份**：无论用哪种模式，都应定期把 RDB 文件备份到异地，用于灾备恢复。
- **主从架构**：RDB 也承担着主从复制时**全量同步**的职责，即使关闭了自动持久化，从节点加入集群时主节点仍可能临时生成 RDB。
