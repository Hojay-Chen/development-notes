# 一、一致性哈希篇

## 1. 为什么需要一致性哈希？

### 1.1 从取模哈希说起

在分布式系统（比如分布式缓存、分库分表）中，我们需要把海量的请求或数据**分散到多台服务器**上。最朴素直观的方案就是**取模哈希**：

```
server = hash(key) % N      // N 为服务器数量
```

例如有 3 台缓存服务器，key 经过哈希后再对 3 取模，结果为 0/1/2，分别落到对应的机器上。这种方式在**节点数量固定**时工作得很好，key 的分布也很均匀。

### 1.2 取模哈希的致命问题

问题出在**节点数量 $N$ 发生变化**的时候。分布式系统的节点随时可能扩容（加机器）或缩容（机器宕机），一旦 $N$ 改变，`hash(key) % N` 的结果就会大面积改变。

![取模哈希的问题](https://raw.githubusercontent.com/Hojay-Chen/development-note-resource/main/images/consistent_hash_modulo.png)

如上图所示，当服务器从 3 台扩容到 4 台时，几乎**所有的 key 都要重新分配**到新的机器上。这会带来灾难性的后果：

- **缓存集体失效**：原本缓存在旧机器上的数据，由于归属机器变了，请求再也找不到，于是全部回源到数据库。
- **缓存雪崩**：瞬间海量请求涌向数据库，可能直接把数据库压垮。
- **大规模数据迁移**：分库分表场景下，几乎所有数据都要搬家，代价极高。

> **核心矛盾**：取模哈希把 key 的归属与节点总数 $N$ 强绑定，$N$ 一变，全局洗牌。我们需要一种**当节点增减时，只有尽量少的数据发生迁移**的算法——这就是**一致性哈希（Consistent Hashing）**。

---

## 2. 一致性哈希原理

### 2.1 哈希环

一致性哈希的核心思想是：**把整个哈希值空间组织成一个虚拟的圆环**。

假设有一个哈希函数输出范围为 $[0,\ 2^{32}-1]$，我们把这个首尾相连的区间想象成一个环（哈希环）：

- **节点映射**：每一台服务器根据其 IP 或主机名计算哈希值，落在环上的某个点。
- **数据映射**：每一条数据（key）也用**同一个哈希函数**计算哈希值，落在环上的某个点。

![一致性哈希环](https://raw.githubusercontent.com/Hojay-Chen/development-note-resource/main/images/consistent_hash_ring.png)

### 2.2 路由规则：顺时针找节点

数据落到环上之后，该由哪个节点来承载呢？规则非常简单：

> 从数据所在的点出发，**沿环顺时针方向**遇到的**第一个节点**，就是该数据的归属节点。

如上图，`k3` 顺时针遇到的第一个节点是 `Node C`，所以 `k3` 由 `Node C` 存储。

理解这个规则后，一致性哈希最关键的优点就浮现出来了：**节点和数据都被映射到同一个环上，数据的归属只取决于它在环上的位置和它顺时针方向的邻居，而与节点总数 $N$ 无关。**

---

## 3. 节点变动时的数据迁移

一致性哈希最大的价值，体现在节点增减时**极小的数据迁移量**。

### 3.1 节点宕机（缩容）

假设 `Node C` 宕机了，会发生什么？原本由 `Node C` 承载的数据（即环上从上一个节点顺时针到 `Node C` 这一段的数据），需要交给**顺时针方向的下一个节点** `Node D`。其余节点的数据**完全不受影响**。

![节点宕机时的数据迁移](https://raw.githubusercontent.com/Hojay-Chen/development-note-resource/main/images/consistent_hash_node_down.png)

可以看到，只有 `k4` 这一小部分数据从 `Node C` 迁移到了 `Node D`，`Node A`、`Node B` 上的数据纹丝不动。

### 3.2 新增节点（扩容）

反过来，当我们在环上 `Node B` 和 `Node D` 之间新增一个 `Node C` 时，只有**落入新节点区间**的那一小段数据需要迁移过来，其他数据同样不动。

![新增节点时的数据迁移](https://raw.githubusercontent.com/Hojay-Chen/development-note-resource/main/images/consistent_hash_add_node.png)

新增 `Node C` 后，`k4` 落在了 `Node B` 到 `Node C` 的区间内，于是 `k4` 从 `Node D` 迁移到新节点 `Node C`，其余 key 归属不变。

> **对比取模哈希**：取模哈希扩容时几乎所有数据都要迁移；一致性哈希扩容/缩容时，**只有受影响区间的那一小段数据需要搬家**，迁移量从 $O(全部)$ 降到了 $O(1/N)$。

## 4. 数据倾斜与虚拟节点

### 4.1 问题：数据倾斜

前面看着都很美好，但有一个隐患：**节点在环上的分布不一定均匀**。

当节点很少时，很可能出现某些节点占据了环上超大的一段区间，而另一些节点只占很小的区间，导致大部分数据都涌向那一个节点，这就是**数据倾斜（Data Skew）**。

![数据倾斜](https://raw.githubusercontent.com/Hojay-Chen/development-note-resource/main/images/consistent_hash_skew.png)

如上图，`Node A` 和 `Node B` 挤在环的一小段，而 `Node C` 独占了从 `Node B` 顺时针到 `Node C` 的超大区间，导致绝大多数 key 都落到了 `Node C` 上，负载严重不均。

### 4.2 解决方案：虚拟节点

为了解决数据倾斜，引入**虚拟节点（Virtual Node）**机制：

- 每个物理节点不再只映射到环上的一个点，而是映射到**多个虚拟节点**（例如 `NodeA_1`、`NodeA_2`、`NodeA_3` ……）。
- 虚拟节点本质上就是用不同的 key（如 `IP + 编号`）再算一次哈希，散布在环上各处。
- 数据路由时仍然按顺时针找虚拟节点，再由虚拟节点还原到对应的物理节点。

![虚拟节点](https://raw.githubusercontent.com/Hojay-Chen/development-note-resource/main/images/consistent_hash_virtual_nodes.png)

如上图右侧，引入虚拟节点后，3 个物理节点在环上变成了 12 个虚拟节点，分布变得非常均匀，数据倾斜问题被极大缓解。

**虚拟节点的优点：**

1. **负载均衡**：虚拟节点越多，物理节点在环上的分布越均匀，数据分布也就越均衡。
2. **平滑迁移**：当某个物理节点下线时，它散落在环上各处的多个虚拟节点会**均匀地**分担给不同的物理节点，而不是把所有压力都压到顺时针的下一个邻居上。
3. **权重控制**：可以为性能更强的机器分配更多的虚拟节点，从而承担更多的负载（按权重分配）。

> **实践经验**：虚拟节点数一般取一个较大的值（如每个物理节点 150~200 个虚拟节点），在均匀性和内存开销之间取得平衡。虚拟节点数越多，分布越均匀，但路由表的内存占用也越大。

## 5. 总结与对比

### 5.1 取模哈希 vs 一致性哈希

两者在映射方式、节点变动影响、负载均衡等方面差异明显，对比如下：

| 特性 | 取模哈希 | 一致性哈希 |
| :--- | :--- | :--- |
| **映射方式** | `hash(key) % N` | 映射到哈希环，顺时针查找 |
| **扩容/缩容影响** | 几乎所有数据迁移 | 仅局部数据迁移 |
| **负载均衡** | 节点固定时较均匀 | 依赖虚拟节点数量，配合虚拟节点后均匀 |
| **节点权重** | 难以支持 | 可通过虚拟节点数量灵活控制 |
| **实现复杂度** | 简单 | 较复杂（需维护环 + 虚拟节点） |
| **适用场景** | 节点数量固定不变 | 动态扩缩容的分布式系统 |

### 5.2 一致性哈希的核心要点

1. **哈希环**：把 $[0,\ 2^{32}-1]$ 的哈希空间首尾相连成环，节点和数据都映射到环上。
2. **顺时针路由**：数据顺时针遇到的第一个节点即为归属节点。
3. **最小化迁移**：节点增减时，只有受影响区间的少量数据需要迁移。
4. **虚拟节点**：用多个虚拟节点打散物理节点，解决数据倾斜、实现负载均衡与平滑迁移。

### 5.3 典型应用场景

- **分布式缓存**：如 Memcached 的客户端分片、Redis Cluster 的哈希槽（哈希槽是一致性哈希思想的工程化变体）。
- **负载均衡**：如 Nginx 的 `consistent_hash` 指令、Dubbo 的一致性哈希路由。
- **分布式存储/数据库**：如 Amazon DynamoDB、Apache Cassandra 的数据分区。
- **分库分表**：ShardingSphere 等中间件中用于数据分片路由。
